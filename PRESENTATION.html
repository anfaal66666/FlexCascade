Introduction

Imagine you find an unmarked legal document — no header, no case number. Can a machine read the text and figure out which of the 161 U.S. courts wrote it? That is exactly what FlexCascade does.

Why Does This Matter?

  • Legal research databases need accurate metadata
  • Millions of scanned/digitised opinions lack issuer labels
  • Manual classification is expensive — automation saves thousands of hours
  • Foundation for jurisdiction-aware legal AI systems

Scale of the Challenge

Our Approach

A two-stage cascade: first predict the state (10 classes), then predict the specific court within that state (up to 88 classes). This breaks a hard 161-class problem into two easier steps.

Plan Changes (What Shifted)

  • XGBoost removed — algorithm fundamentally incompatible with 98%-sparse TF-IDF features (scored only 10.3%)
  • Flat classifier added — a non-cascade flat-state model outperformed the cascade design, changing our final recommendation
  • Streaming pipeline — original plan to load full CSV into memory was replaced with DuckDB streaming due to 750 GB raw data size
  • States limited to top-10 — class imbalance in rare states led to pruning from all 50 to top 10 by frequency

Methodology Overview

  • Data source: CourtListener bulk S3 + HuggingFace case-law
  • Text features: TF-IDF (12,000 dimensions, bigrams)
  • Algorithms: SVM · Random Forest · XGBoost
  • Architectures: Flat · Plain Cascade · Cascade+Fallback
  • Evaluation: Stratified 60/20/20 split, macro F1 + accuracy
  • Language: Python (pipeline) + R (modeling)

Key Processing Steps

  • Streaming decompression — bz2 files read in 8MB chunks, never fully loaded into RAM
  • DuckDB SQL join — clusters → dockets → courts in a single in-memory OLAP query
  • HTML stripping — regex removes all <tags> and collapses whitespace
  • State derivation — extracted from court jurisdiction field, not raw text
  • Opinion aggregation — multiple opinions per cluster joined with separator

R-Side Normalization

After loading the CSV in R: NA → empty string · whitespace collapse · timestamp parsing · drop rows missing document/state/issuer · prune issuers with fewer than 10 cases

Slide 8 · Model Architecture

How the Cascade Classifier Works

Cascade Architecture (2-Stage)

Stage 1 · State Classifier
Input: TF-IDF 12K · Output: 1 of 10 states
↓
Stage 2a
State A court classifier
Stage 2b
State B court classifier
… 10 total
↓ (if confidence < 0.55)
Fallback · Global Issuer Classifier
Catches uncertain state predictions

Why a Cascade?

Predicting directly from text to 1-of-161 courts is a hard problem. By first narrowing to a state (1-of-10), each per-state classifier faces a much smaller class set (avg ~16 courts per state), making it easier to learn distinguishing patterns.

Four Architectures Tested

ArchitectureDescription
Flat StatePredict state only (10 classes) — best accuracy
Flat IssuerPredict court directly (161 classes)
Plain CascadeState → per-state issuer model
Cascade+FallbackCascade + global fallback on low confidence

Algorithms

Random Forest

Ensemble of decision trees. Handles class imbalance via bootstrap. Best for sparse TF-IDF.

SVM

Linear maximum-margin classifier. Strong on sparse high-dim text. Our baseline.

XGBoost

Gradient-boosted trees. Designed for dense tabular data — struggled with 98% sparse input.

Surprise Finding

The simplest architecture — Flat State (predict just the state) — beat all cascade variants. Cascade degradation from compounding errors outweighed the benefit of smaller per-state classifiers.

XGBoost — Why It Failed

XGBoost scored only 10.3% accuracy (barely above random). Root cause: XGBoost's tree splits are inefficient on 98%-sparse matrices. Tripling iterations (100→500) and tuning 5 hyperparameters raised accuracy only 0.1%. Algorithm abandoned.

Slide 10 · Conclusions & Future Work

Key Takeaways & What Comes Next

What Worked

  • Random Forest + TF-IDF — simple and powerful for sparse text, 97.53% accuracy
  • Streaming DuckDB pipeline — processed 750 GB without exceeding 8 GB RAM
  • Ensemble methods beat single models — RF outperformed SVM by 1.5%
  • Flat classifier beat cascade — simpler is better when stage-1 accuracy is high
  • Perfect data quality — 100% field completeness drove consistent results

Lessons Learned

  • Match algorithm to feature space (XGBoost ≠ sparse TF-IDF)
  • Cascade errors compound — only use cascades when stage-1 error is very low
  • Data quality matters more than hyperparameter tuning
  • Always have a fallback model (SVM at 96% here)
